Component Library

Rebulding a design system into a scalable, front-end-ready library

  • Role:Designer
  • Duration: 3 months
  • Tools: Figma (Variants, Auto Layout), Atomic Design
  • Scope: 30+ components - inputs, navigation, calendar, buttons and interactive states

The problem

The team was working from and existing component library, but it had drifted out of sync with the product: components were outdated, inconsistently named, inconsistenty with color and missing states. There was a visual inconsistency across the product that made it feel unpolished and unprofessional.

There was no single source of truth, and no shared tooling to build one in.

My approach

I rebuilt the library from scratch in Figma, migrating it off Adobe XD and using the move as an opportunity to fix the underlying structure rather than just porting old components over. I applied Atomic Design principles — starting from foundational tokens (color, spacing, type) and composing up through atoms (buttons, inputs) to composite patterns (selects, calendars, search fields) — and refreshed the visual language along the way so the library matched the current product, not the old one.

Key decisions:

  • Systematic sizing, not one-off variants.Core components like buttons and inputs were built as full size scales (XS through XL) rather than single fixed instances — so product teams could pull the right density for a given context (dense tables vs. primary CTAs) without creating a new component every time.
  • Consolidated states inside each component setButtons, inputs, checkboxes, and radios each live as a single component set with every state (default, hover, disabled, focus) as variants — reducing the surface area designers had to search through and keeping states from drifting apart over time.
  • Built composite patterns on top of atoms, not from scratchMore complex pieces — like the Search with Multiselect field, or the Calendar/date-picker system (with both compact and expanded layouts) — were assembled from the same base inputs and selects, so fixing an atom would propagate cleanly instead of requiring parallel fixes.
  • Named and structured for developer handoff, not just design.Since I work with HTML/CSS/SCSS myself, I structured naming and hierarchy to map cleanly onto how these components would actually get built — reducing back-and-forth in implementation.

Outcome

The result was a single, trustworthy source of components that replaced the old fragmented library. Designers had one place to work from instead of rebuilding basics; developers had a clearer, more consistent reference for implementation. It also directly shaped how I think about design work now — systems-first, with front-end feasibility built in from the start rather than bolted on later.

What I'd do differently

If I did this again, I would share early component sets with the team, rather than waiting until thee library felt more complete. Since I had to redo the buttons component to unify all in a big component set.

In addition, looking back, I would map the most-used components from the old library, and prioritize rebuilding those first, that would have gotten the team off the outdated system faster.
