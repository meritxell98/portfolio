Component Library

Rebulding a design system into a scalable, front-end-ready library

  • Role:Designer
  • Duration: 3 months
  • Tools: Figma (Variants, Auto Layout), Atomic Design
  • Scope: 30-50 components - inputs, navigation, calendar, buttons and interactive states

The problem

The team was working from and existing component library, but it had drifted out of sync with the product: components were outdated, inconsistently named, inconsistenty with color and missing states. There was a visual inconsistency across the product that made it feel unpolished and unprofessional.

There was no single source of truth. Every fix had to be made in multiple places, and handoof to development was slow because enfineews couldn't be sure which version of a component was current.

My approach

I rebuilt the library from the ground up using Atomic Design principles. From foundation tokens (color, typography) and compposing up through atoms (buttons, inputs, icons) to molecules (form files) to more complex, reusable patters(navigation, calendar).

Key decisions:

  • Consolidated variants over one-off components.Instead of separate components for each button state, I used Figma Variants so every state (default, hover, disabled, active) lived inside one component, reducing the surface area designers had to search through and keeping states from drifting apart

Outcome

The result was a single, trustworthy source of components that replaced the old and fragmented library. Trustworthy source of components taht replaceed the old fragmented library. Also, it directly shaped how I think about design work now, systems-first, with front-end feasibitly built in from the start.

What I'd do differently

For this project I used styles, but if i had do redo it again I would use variables for color tipography and spacing. This would make it easier to update the library in the future, and would allow for more flexibility in theming.
