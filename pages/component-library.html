Component Library

Rebuilding a fragmented design system into a scalable, front-end-ready library.

Role
Sole designer, end to end
Tools
Figma (Variants, Auto Layout), Atomic Design
Scope
30+ components — buttons, inputs, selects, calendar system, checkboxes, radios, breadcrumbs, composite patterns

The problem

The existing library lived in Adobe XD, not Figma — already a mismatch with how the rest of the team was working. Beyond the tooling gap, the file itself had no real structure: components weren't organized by type or hierarchy, naming was inconsistent, and the visual style was outdated relative to where the product had moved.

In practice, this meant designers couldn't trust or quickly find what they needed, so they'd end up recreating basics from scratch — leading to visual inconsistency across the product and duplicated work every time something needed updating. There was no single source of truth, and no shared tooling to build one in.

My approach

I rebuilt the library from scratch in Figma, migrating it off Adobe XD and using the move as an opportunity to fix the underlying structure rather than just porting old components over. I applied Atomic Design principles — starting from foundational tokens (color, spacing, type) and composing up through atoms (buttons, inputs) to composite patterns (selects, calendars, search fields) — and refreshed the visual language along the way so the library matched the current product, not the old one.

  • Systematic sizing, not one-off variants. Core components like buttons and inputs were built as full size scales (XS through XL) rather than single fixed instances — so product teams could pull the right density for a given context without creating a new component every time.
  • Consolidated states inside each component set. Buttons, inputs, checkboxes, and radios each live as a single component set with every state (default, hover, disabled, focus) as variants — reducing the surface area designers had to search through and keeping states from drifting apart over time.
  • Built composite patterns on top of atoms, not from scratch. More complex pieces — like the Search with Multiselect field, or the Calendar/date-picker system (with both compact and expanded layouts) — were assembled from the same base inputs and selects, so fixing an atom would propagate cleanly instead of requiring parallel fixes.
  • Named and structured for developer handoff, not just design. Since I work with HTML/CSS/SCSS myself, I structured naming and hierarchy to map cleanly onto how these components would actually get built — reducing back-and-forth in implementation.

Outcome

The result was a single, trustworthy source of components that replaced the old fragmented library. Designers had one place to work from instead of rebuilding basics; developers had a clearer, more consistent reference for implementation. It also directly shaped how I think about design work now — systems-first, with front-end feasibility built in from the start rather than bolted on later.

What I'd do differently

If I did this again, I would share early component sets with the team, rather than waiting until thee library felt more complete. Since I had to redo the buttons component to unify all in a big component set.

In addition, looking back, I would map the most-used components from the old library, and prioritize rebuilding those first, that would have gotten the team off the outdated system faster.
